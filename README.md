# Maintainability evaluation framework

A tool for measuring the maintainability of MERN applications (MongoDB, Express, React, Node) with **11 decision points**
grouped into 4 subcharacteristics (Testability, Analyzability, Modularity, Modifiability). It was designed to compare
applications generated by AI agents from specifications with different levels of detail, but it evaluates
any application with a `backend/` + `frontend/` structure.

What it does: reads the code, queries the npm registry, runs the app's tests, computes coupling metrics with DV8
and builds a profile with a score from 0 to 100. Whatever cannot be decided automatically is left **pending** and the result is
expressed as a **range** until a person completes it.

> **Security.** Evaluating with tests (`--run-tests`, the default behavior of `evaluate`) installs dependencies and
> runs code generated by a model, which is untrusted. Do it in a disposable virtual machine or container, or use
> `--skip-tests`.

## Requirements

| Requirement | Notes |
|---|---|
| Python ≥ 3.9 | Standard library only: there is no `pip install`. |
| Node.js ≥ 18 and npm | Used for code analysis and npm queries. |
| `npm install` in this folder | Installs `ts-morph`, `dependency-cruiser`, `depcheck`, `spectral`, `c8`, `jscpd`. |
| DV8 (optional) | For DL and PC. Without it those criteria stay pending. Set `DV8_CONSOLE` if it is not at the default path. |
| Network (optional) | npm versions and vulnerabilities. Without a network use `--offline`. |

```
npm install
python cli.py doctor        # checks all of the above and tells you what is missing
```

## Usage: three steps

**1. Create the applications.** One folder per application inside `apps/`, named `<agent>-<level>`
(for example `apps/claude-n1`). Each must have `backend/` and `frontend/`. Instructions for generating them with an
agent, without one level contaminating another, are in [docs/generating-apps.md](docs/generating-apps.md).

**2. Evaluate everything.**

```
python cli.py evaluate --model "<model that generated the apps>"
```

For each app it evaluates the 11 points, runs the tests, computes DL and PC with DV8, leaves the manual review templates and
finally aggregates the results. Useful options: `--skip-tests`, `--skip-dv8`, `--offline`, `--accept-heuristics`, or
pass specific folders (`python cli.py evaluate path/app1 path/app2`). You can fix the options in `experiment.json`
(copy [experiment.example.json](experiment.example.json)).

**3. View the results.** Open `results/report.md` (regenerated with `python cli.py report`). It has the overall result,
a risk dashboard (semaphore per subcharacteristic, heat map, not-evaluable points, hotspots), a ranked risk heat map, the matrix of the 11 points, the pending manual reviews, the findings, the methodological warnings and the environment.
There is a [real example](example/example-report.md).

### Closing the ranges: manual review

As long as there are criteria the program cannot decide, the scores are ranges. For each app, in
`results/<app>/`:

1. Read `manual_review.md`: statement of each pending criterion, evidence and a suggestion.
2. Copy `manual_review.draft.json` to `manual_review.json` and change `ok` to `true` or `false`.
3. Run `python cli.py evaluate` again. The file is read automatically.

Details in [docs/manual-review.md](docs/manual-review.md).

## Repository contents

| Path | What it is for |
|---|---|
| `cli.py` | Entry point: `doctor`, `evaluate`, `report`. |
| `evaluate.py` | Core: collects evidence, evaluates the 11 points, computes the profile and aggregates. |
| `ast_metrics.js` | Code analysis with ts-morph (complexity, classes, literals, schemas, routes…). |
| `dv8_metrics.py` | Computes DL and PC with DV8 from the dependency graph. |
| `manual_template.py` | Generates the guide and draft for the manual review. |
| `relational_schema.py`, `relational_analysis.py` | Extract the relational schema from SQL files and Sequelize migrations/models, and measure the data model criteria (including the ER comparison). |
| `pg_analysis.py`, `pg_schema.js`, `pg_seed.py`, `pg_runtime.py` | Analyze the data model on a real PostgreSQL database: `--postgres` in `cli.py evaluate` (needs `PG_ADMIN_URL`). See `docs/methodology.md`. |
| `judge.py` | A model different from the generator decides the pending design-judgment criteria (`--judge` in `cli.py evaluate`). See `docs/manual-review.md`. |
| `rubric.json` | **All the framework's thresholds, weights and lists** (including the input-artifact table and the dashboard cut-offs). Adjust it here, not in the code. |
| `dv8/matrix-template.json` | Template of the dependency matrix consumed by DV8. |
| `specs/` | Technical specifications N1–N3, domain requirements and the generation prompt. |
| `run_experiment.py`, `acceptance_check.py` | Optional: generate apps with an agent's CLI and test them against PostgreSQL started from each app's own `docker-compose.yml` (needs Docker; without it the gate is skipped with a message). |
| `docs/` | Methodology, limitations and guides. |
| `tests/` | Tests of the evaluator itself: `python -m unittest discover -s tests -v`. |
| `example/` | Report from a real run. |

## Adapting it

The thresholds, weights, table of supported runtimes, directories of each layer and library lists are in
`rubric.json`. The `supported_runtimes` table is a working assumption: **verify it against the official pages before
freezing an experiment**. If you change the rubric, run the evaluator's tests.
