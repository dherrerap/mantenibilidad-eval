# Maintainability evaluation framework

A tool for measuring the maintainability of web applications built on the PERN stack (PostgreSQL, Express, React, Node) with **11 decision points**
grouped into 4 subcharacteristics (Testability, Analyzability, Modularity, Modifiability). It was designed to compare
applications generated by AI agents from specifications with different levels of detail, but it evaluates
any application with a `backend/` + `frontend/` structure.

What it does: reads the code, queries the npm registry, runs the app's tests, computes coupling metrics with DV8
and builds a profile with a score from 0 to 100. Next to the score it reports the **tokens** the AI agent consumed to create each
application (phase *initial*) and to implement the additional requirements on top of it (phase *R2*). Whatever cannot be decided automatically is left **pending** and the result is
expressed as a **range** until a person completes it.

> **Security.** Evaluating with tests (`--run-tests`, the default behavior of `evaluate`) installs dependencies and
> runs code generated by a model, which is untrusted. Do it in a disposable virtual machine or container, or use
> `--skip-tests`.

## Requirements

| Requirement | Notes |
|---|---|
| Python ≥ 3.9 | Standard library only: there is no `pip install`. |
| Node.js 20.19+, 22.13+ or 24+, and npm | Used for code analysis and npm queries. ESLint 10 and Knip 6 need those lines (Node 22 LTS recommended); `--mutation` (StrykerJS 10) needs Node 22 or later. |
| `npm install` in this folder | Installs `ts-morph`, `dependency-cruiser`, `knip`, `spectral`, `c8`, `jscpd`, `pg`, `eslint` with `eslint-plugin-sonarjs` and `typescript-eslint`, and the optional `@stoplight/prism-cli` (runtime contract conformance) and `@stryker-mutator/core` (`--mutation`). |
| DV8 (optional) | For DL and PC. Without it those criteria stay pending. Set `DV8_CONSOLE` if it is not at the default path. |
| Network (optional) | npm versions and release dates, vulnerabilities (OSV, api.osv.dev) and the PostgreSQL/Node/React/Express support dates of endoflife.date, all as of `--as-of` (default today). Without a network use `--offline`. |
| Docker + Docker Compose (optional) | Only for the acceptance gate of `run_experiment.py`, which starts PostgreSQL from each app's own `docker-compose.yml`. Without Docker the gate is skipped with a message. |
| PostgreSQL (optional) | Only for `--postgres` (acceptance gate, contract conformance and live database analysis): either the server binaries installed locally, from which a temporary server is started and deleted (`pg_temp.py`; `PG_BIN` if they are not found), or a role with `CREATEDB` in `PG_ADMIN_URL`. Without it the data model is evaluated from the code (SQL files, Sequelize migrations and models) and the gate does not run. |

```
npm install
python cli.py doctor        # checks all of the above and tells you what is missing
```

## Usage: three steps

**1. Create the applications and measure their tokens.** One folder per application inside `apps/`, named `<agent>-<level>`
(for example `apps/claude-n1`) or `<agent>-<domain>-<level>` (for example `apps/claude-cinema-n1`; the domain must have a
`specs/requirements-<domain>.md`, and it then takes precedence over `--domain`). Each must have `backend/` and `frontend/`. Each app goes through two phases, each in its own agent
session: **initial** (create it from `specs/combiner-prompt.md`) and **r2** (implement `specs/r2-additional-requirements.md` on top of it
with `specs/r2-prompt.md`). Record the tokens of each phase:

```
python token_usage.py scan                                   # finds the Claude Code / Codex sessions of each app and suggests the commands
python token_usage.py record apps/claude-n1 --phase initial --from <transcript>
python token_usage.py record apps/claude-n1 --phase r2      --from <transcript>
python token_usage.py show
```

`run_experiment.py --phase initial,r2` does both phases and records the tokens by itself. Instructions for generating the apps without one
level contaminating another, and for measuring the tokens, are in [docs/generating-apps.md](docs/generating-apps.md).

**2. Evaluate everything.**

```
python cli.py evaluate --model "<model that generated the apps>"
```

Add `--as-of YYYY-MM-DD` with the generation date to fix the versions, advisories and supported runtimes at that date, so that evaluating
again later gives the same result (default: the evaluation date).

`--model` is required: the generator model is a variable of the experiment. Without it the command stops with an error; `--allow-missing-model`
evaluates anyway, and then `profile.md` and `report.md` carry a prominent warning. The model is recorded in `results/environment.json`.

For each app it evaluates the 11 points, runs the tests, computes DL and PC with DV8, leaves the manual review templates and
finally aggregates the results. Useful options: `--skip-tests`, `--skip-dv8`, `--offline`, `--accept-heuristics`,
`--mutation` (mutation testing of the apps' own tests with StrykerJS: informational and slow, up to 30 minutes per package), or
pass specific folders (`python cli.py evaluate path/app1 path/app2`). You can fix the options in `experiment.json`
(copy [experiment.example.json](experiment.example.json)).

**3. View the results.** Open `results/report.md` (regenerated with `python cli.py report`). It has the overall result,
its sensitivity to the weights (ranking under uniform weights, equal points and each point removed), the ISO/IEC 5055 weaknesses with their density per KLOC, the AI token consumption (initial, R2 and R2 / initial), a risk dashboard (semaphore per subcharacteristic, heat map, not-evaluable points, hotspots), a ranked risk heat map, the matrix of the 11 points, the pending manual reviews, the findings, the methodological warnings and the environment.
[example/](example/) keeps a report of the earlier MERN version (v0.1.0-mern) for reference only: its sections and its data model
point do not match the current framework.

### Closing the ranges: manual review

As long as there are criteria the program cannot decide, the scores are ranges. For each app, in
`results/<app>/`:

1. Read `manual_review.md`: statement of each pending criterion, evidence and a suggestion.
2. Copy `manual_review.draft.json` to `manual_review.json` and change `ok` to `true` or `false`.
3. Run `python cli.py evaluate --rescore`. The file is read automatically and only the scoring is redone, from the evidence already
   collected (`results/<run>/metrics.json`): no tests, npm queries or DV8 again.

Details in [docs/manual-review.md](docs/manual-review.md).

## Scope

Applications on the PERN stack with a `backend/` + `frontend/` structure whose data layer is PostgreSQL. The relational schema is read from SQL
files, Sequelize migrations or Sequelize models (Level 1 and 2 apps may use any access library, but the schema is only visible to the evaluator
through one of those three); apps that define their schema only with Knex, Prisma's `schema.prisma`, TypeORM or `sequelize-typescript`
decorators have no `data_schema` artifact and the *Data model design* point is reported as not evaluable. Details in [docs/limitations.md](docs/limitations.md).

The first pilot (EXP-01) used the MERN stack and was evaluated with the previous version of this tool, tagged `v0.1.0-mern`.

## Adapting it

The thresholds, weights, table of supported runtimes, directories of each layer and library lists are in
`rubric.json`. The `supported_runtimes` table is a working assumption: **verify it against the official pages before
freezing an experiment**. If you change the rubric, run the evaluator's tests.

To change how a decision point is measured, edit only its module in `evaluator/points/` (for example
`evaluator/points/coupling.py`): each one exposes a function `eval_<id>(m, manual, opts)` that returns the criteria, metrics,
evidence, finding and, if any, forced levels, and is registered in `evaluator/points/__init__.py`. A new source of evidence goes in
its own module of `evaluator/collectors/` and is called from `collectors.collect()`. The evidence (`m`) is saved as
`results/<run>/metrics.json`, so a point can be re-scored without collecting again (`python evaluate.py aggregate results`).
